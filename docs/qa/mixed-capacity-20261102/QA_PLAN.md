# S16C 混合负载与故障容量实验

用户授权执行S16C；前置S16B/S10F/S11E已完成。验收范围遵守[实施切片](../../design/knowledge-first-20261020/IMPLEMENTATION_SLICES.md#s16c--代表负载与故障容量报告)与[C-CAPACITY](../../design/knowledge-first-20261020/CAPACITY_CONTRACTS.md)。同一Agent顺序执行测试建设与独立检查，无并行Agent。

| LC02 | 常规负载与突发热点 | 受理/完成/排队P50/P95/P99及样本量、拒绝/错误率、资源与配额；明确闭环并发负载及测试模型延迟，不冒充生产容量 |

## 实验条件

- 每次运行生成唯一`agentic_{knowledge,tasks}_test_s16c_<run>`数据库，复用既有test应用DML/迁移DDL账号。MySQL、PG、S3与搜索服务真实运行；对象/索引复用登记test命名空间，合成租户和所有业务ID唯一。保留数据及日志，不执行清库、删索引或删卷。
- Knowledge一个实例：每租户入库1、在线搜索1、候选回调2、在途及排队入库6；Tasks一个实例：每租户交互1、后台1、每lane在途及排队4。每服务Hikari最大6，Java堆上限384MiB。跨实例准入沿S16B证据，本片测真实混合竞争。
- 两个Python worker，各固定一个租户且每进程一个在途；QA v2与研究v4轮询；各PG最大2、Tasks HTTP4、Knowledge HTTP2，聚合PG4/Tasks HTTP8/Knowledge HTTP4。Python HTTP处理4、在线检索2。无外部模型连接，向量替身固定80ms，Chat固定150ms；这些数字均是实验值。
- 预发布每租户2份单块文本作为固定检索集合；测量上传使用不同长度的小文本。先预热1轮，再常规4轮；突发A每类型12、B每类型2及12次在线检索；故障后再测2轮。资料数量、实际源字节/分块与最终结果以收据为准。
- 约0.4秒加采样开销读取真实Prometheus/进程RSS与CPU/两域有效租约。容量报告明确采样盲区、共享宿主干扰、代理开销、小样本分位数、闭环负载和模型替身边界。
- 数据库锁仅使用本轮schema；双索引故障在本轮loopback代理注入，不改变共享服务；模型故障只有本轮测试目录开关；进程操作只作用于本轮记录PID。

## 复现与证据

在已有登记本地test基础设施和私密配置的本项目目录执行：

```sh
mvn -B -ntp -pl knowledge-service,async-task-service -am package
python3 deploy/capacity_validation.py
```

入口将stdout限制为结果路径；详细日志在`.logs/s16c-<run>/`，私密运行收据由`.local/s16c-latest.json`指向，故障/测量保存在`measurements.json`。默认`pytest`跳过该有状态实验，显式运行必须通过本入口；默认跳过不计作本片验收通过。未提供真实生产U06目标，报告只陈述本次观测，不承诺SLA。

源码审查重点：不能吞掉资源采样异常；成功率与拒绝率分开；不能通过直接更新状态制造成功；故障失败资料不可发布；只在唯一数据库上注入锁；同一受理ID故障重试须可对账；最后进程/原账本核对。
