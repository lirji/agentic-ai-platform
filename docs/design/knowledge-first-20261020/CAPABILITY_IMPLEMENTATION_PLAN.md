## 1. 框架与服务分工

| 承载方 | 本轮规划中的实际职责 | 保持的边界 |
| --- | --- | --- |
| **LlamaIndex** | 结构化资料到 Document/Node、结构分块、授权 Retriever 组合、RRF、独立模型重排适配、证据整理、检索指标适配 | 不拥有业务版本/权限/发布状态；不直接写 Qdrant/ES；不另起顶层 Workflow；不隐式使用全局 Settings/默认模型 |
| **LangGraph** | 问答、评测和研究的执行步骤、取消、受控恢复、检查点与中央任务对账 | 复用现有 PG 与 epoch fencing；不替代 Java 的审批、发布或预算账本 |
| **Deep Agents** | 复杂研究的规划、受控工具调用、按问题组织证据、生成报告与资料助手结果 | 保留工具白名单及预算；首批不默认启用子 Agent、shell、文件系统或内部 saver；长期记忆经 Java 治理 API 访问 |
| **knowledge-service / Java** | 原文、解析作业、文档/索引版本、准备结果、唯一索引提交、授权候选与引用复核、评测定义/报告、反馈和知识发布 | MySQL/S3 为权威；所有新 SQL 用 MyBatis-Plus/Mapper XML，迁移不改写旧版；模型生成内容不冒充原文 |
| **async-task-service / Java** | 通用 AI 任务、租约、事件、取消/恢复；拟增加独立 `usage` 逻辑模块承载共享额度账本 | 任务状态与业务状态分开；usage 不复制框架状态，不共享其他服务写库；是否拆独立计量服务留到明确规模驱动 |
| **conversation-service / Java** | 会话、可靠交接、上下文引用及可选画像治理 | Java 拥有记忆确认/遗忘/代次；PG checkpoint 不自动成为用户长期记忆权威 |
| **edge-gateway + 已选 IAM** | 正式身份交换、路由与可信上下文；服务继续校验业务权限 | 沿用 Casdoor/auth-platform 方向，不重建用户中心；组织/共享策略与实际接入条件在相应任务冻结 |
| **React 工作台** | 资料、评测、反馈/运营、共享、会话/研究、记忆等完整用户任务 | 沿现有路由、Ant Design、TanStack Query、Axios/SSE 与错误目录；真实 API 可用才开放入口，不先放占位菜单 |

上述是本项目的职责选择。框架提供的后处理、评测和持久化接口可复用，业务规则与验证不能省略：[LlamaIndex 后处理](https://developers.llamaindex.ai/python/framework/module_guides/querying/node_postprocessors/)、[评测](https://developers.llamaindex.ai/python/framework/module_guides/evaluating/)、[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)。

## 3. 三条关键实施路径

### 3.1 检索编排移交及独立模型精排

**现状保留为基线：** Java 两路候选 → RRF60 → 权威发布/权限/摘要过滤 → Top K；问答目前 K=5。不能再把这段描述为待建设。

**目标链路：**

```text
用户搜索 / 问答图 / 研究工具
  → 同一个 Python RAG 用例（LlamaIndex，明确策略版本）
  → 查询向量 + Java 两路授权候选原语
  → 合法候选去重与 RRF60
  → 独立相关性模型 Reranker
  → Top K
  → Java 最终引用/版本/权限复核
  → 结果；或交给 LangGraph/Deep Agents 后续生成并再次核验
```

实施拆分：

1. **S11A/S11B：先有授权原语。** Java 仅对被授权运行时返回两路候选及权威原文、来源排名、稳定文档/块/批次身份；索引过滤和权威复核都在返回正文前完成。Python 提供经校验的查询向量及模型/维度/策略标识；候选 API 不再反调 Python 的 RAG 路径，避免形成循环编排。最终引用解析为独立权威检查。
2. **S11C：只移交融合，先证明兼容。** 暂不开查询扩展和模型重排。固定候选输入验证去重、排名、同分顺序与 Java 基线一致；真实链路再比较权限与已发布版本结果。新路径只融合一次，旧 Java 路径只服务旧策略/旧任务。
3. **S11D：接一个独立模型。** 优先验证百炼 `qwen3-rerank` 的受控 HTTP 适配，作为 LlamaIndex 后处理组件；该模型调用与聊天生成是不同协议/计费能力，不能把聊天代理默认当作支持重排。另一可选路线为本地 CrossEncoder，仅在部署/数据边界需要时评估，不同时接多个提供方。[百炼重排 API](https://help.aliyun.com/zh/model-studio/rerank)
4. **S11E：三个消费者共用用例。** 搜索页、问答和研究工具切换到同一策略，不留下“搜索已精排而问答仍旧排序”的分叉。记录来源贡献、融合名次、重排名次、耗时、策略和是否降级；正文及诊断权限受控。

**锁定版本特别处理：** 本地 `llama-index-core 0.14.25` 的 `QueryFusionRetriever` 默认 `num_queries=4`，还会解析默认 LLM；其 RRF 用从 0 起的排名和 `node.hash`。当前 Java 语义是一基排名 `1/(60+rank)`，候选身份含 chunk/batchDigest。因此复用 Retriever/Node 扩展接口，但显式实现与当前契约一致的融合适配，不直接用默认构造器，也不把跨文档同文段错误合并。查看时间与源码摘要见 [框架证据](FRAMEWORK_EVIDENCE.json)。

Java 当前先按各路原始名次累计分数，再过滤无效版本/权限。新原语须为合法候选保留内部 `sourceRank`，过滤后不压缩名次，否则即使公式没变也会改变排名。原始名次仅供可信 RAG 适配，外部诊断不暴露无权候选 ID、数量或过滤空位；固定输入对照必须包含这类空位。

精排前保留足够的合法候选，不能先截成 5 条再期望精排找回遗漏。候选池、请求字节/文档数、deadline 和费用有上限；默认是否允许回退在 S11A 冻结。允许回退时必须标明 `RRF_ONLY` 等稳定策略结果，不能把失败隐藏为“已精排”。新模型真实调用前核对账号、地域、端点、价格及独立累计额度，当前计划不新增额度。

### 3.2 原文解析、LlamaIndex 转换与唯一发布

```text
上传 / 更新
  → Java 保存不可变原文件与受理事实
  → 隔离解析进程：PDF / DOCX / 条件 OCR
  → 结构化提取物：正文、页/段/表位置、告警、提取器版本
  → LlamaIndex：结构分块 → Embedding → 准备包
  → Java 校验原文件/提取物/准备包绑定
  → 现有逐 sink 写入与发布机制
  → React 显示真实来源、版本和告警
```

优先沿既有架构让 Java Knowledge 拥有解析作业和有界子进程，复用参考 Tika/PDFBox/POI/Tesseract 的经验；具体依赖、许可证、版本和容器资源在 S9A 通过样本验证后锁定。LlamaIndex 负责规范 Document/Node 与转换，不把 Reader 的存在当作业务解析隔离。若纯 Python Reader 方案在所需格式上更简单，必须在 S9A 明确替代决策，不能两端各自解析同一资料。

P-v2 必须区分**原文件 hash**、**提取物 hash**、**片段原文/元数据 hash**及处理 profile；PDF 页码不能伪装成原始二进制文件的 UTF-8 字节区间。结构化来源允许段/表跨页等情况，不能要求所有格式都还原为一个连续字符区间。

TXT/MD 的 P-v1、旧索引 profile 和在途任务保留兼容；新旧处理版本不能仅因全局常量变化导致旧资料突然不可搜索。S10D 负责版本化重索引、验证、切换和清理资格，清理不是普通发布动作的隐式副作用。

### 3.3 质量、知识运营与任务状态的关系

Java Knowledge 持有评测集/标注版本、运行定义及报告、反馈、候选和发布决策。LangGraph 只执行评测图，复用中央任务的领取/取消/恢复；中央任务终态与评测业务报告通过幂等报告/查询对账关联，不能再建第二个通用任务调度器。

先评测当前真实 Retriever，再评测迁移后的同一 RAG 用例，避免评测走特制优化链路。检索指标统一指定文档/版本/片段身份、Top K 口径、重复命中、无答案与空结果语义；LlamaIndex 指标只作为适配部件。锁定版本部分指标会拒绝空列表，项目必须把合法的空召回计为业务结果，和网络失败、权限变化、评测执行错误区分开。

人工标注与答案评审是第一版标准；在线/离线模型裁判为明确开关，需独立预算和误判校验。历史同一身份快照不意味着有权继续读取后来撤权的正文；评测与报告读取仍复核当前权限。

S8A 至少给出 Recall@K、MRR/nDCG 的相关性标注与聚合口径，另列引用可访问/定位正确、结论受支持、答案覆盖、正确拒答、耗时及费用。有答案题的空召回按未命中计；无答案题按拒答规则计，不能统一记零分。跨文档、冲突/过期资料、缩写/精确词、追问、权限拒绝及恶意指令分别保留问题切片。基线先记录实际值；改善目标与容许退化在运行比较前固定，不能看完结果再移动门槛。

更换 chunker/profile 时按同一原文件及原文位置重绑定相关性标注，分别报告文档口径与片段口径。无法映射时标为不可比，不能拿旧 chunkId 去判定新分块漏召回，也不能为了新算法成绩修改正确答案。

反馈可以早采集；候选编辑、评估、审批、入库发布和发布后验证逐项交付。**LangGraph interrupt 不是业务审批**，模型文本中的“批准/发布成功”不产生业务状态变化。发布成功以 Knowledge 发布事实为准，撤回通过新补偿版本或明确撤下处理。

## 5. 契约、数据与兼容策略

新增需求先进入 [CAPABILITY_CONTRACT_BACKLOG](CAPABILITY_CONTRACT_BACKLOG.md)，每个任务启动前把其必要部分转成唯一正式契约。该文件中的 C-编号是**设计工作包**，不是已经上线的 HTTP API。未定义 schema 时不先做前端伪数据或复制参考 JSON。

- `K/P/Q/T/R02/A01` 当前契约继续有效；可兼容字段也需显式版本规则。旧任务按冻结的 graph/runtime/profile 恢复，不在恢复时换成新算法。
- MySQL 迁移按服务分别串行追加；S8 质量、S9 解析、S10 生命周期、S13 授权、S14 运营不能并行抢同一 Knowledge 迁移编号。表与全部字段必须有注释。
- 新索引 profile 及解析/分块/Embedding 配置作为可追溯处理版本；新增解析器不强迫重算所有旧资料。是否增建集合取决于字段/模型兼容性，在 S10D 按真实变更决定。
- `usage` 共享预算首次落在 Tasks 自有模块/数据库为本计划建议；原因是当前需统一有界 AI 执行的预留和结果未知处理。与任务业务通过公开内部 API 协作，不能把预算字段零散塞进各服务表；后续需要独立计费域时再评估服务抽取。
- 撤权以 Knowledge 的提交事实为准；候选返回、模型外发前、结果交付及恢复分别复核当前权限。已发给模型的请求无法通过事后撤权追回，需记录外发与撤权的时序，并阻止后续输出/再调用；S13 契约明确竞态窗口，不能声称跨服务检查与外发原子提交。
- 原文、准备包、历史引用、评测报告、任务 checkpoint、日志及备份有不同保留规则；删除不承诺立即物理抹除所有副本，恢复时须防止撤下数据重新可见。期限需业务决定，计划不虚构天数。

## 7. 每项任务的完成与交付标准

任务流程固定为：**核对现状 → 冻结当期契约/选型 → 保护受影响行为 → 后端/AI/UI 有界实现 → 实际失败与恢复验证 → 文档与进度 → 独立 Git 交付**。设计/验证任务按其产物验收，不冒充实现。

带 UI 的任务要覆盖成功、空数据、加载、权限拒绝、版本冲突、超时未知结果、重试/恢复；沿已有视觉方向核对 1440/1024/414px 的适用状态和真实截图。数据经 API 获取，演示数据进入隔离数据库，不写死页面。

每个实现任务都要有与本次修改相匹配的证据：真实数据库竞争/事务不用纯 Mock 证明；模型替身证明协议，不证明语义；小样本费用/延迟不冒充总体 SLA。验证失败时修正当前任务并更新检查点，不开启依赖它的任务。

普通软件改动的回退保留旧契约/profile 和兼容数据库；已发生业务效果通过查询对账/补偿处理。允许的正常 Git 提交、合并、推送沿用户持续授权执行；不强推，不绕过必要失败门禁，不自动生产部署。
