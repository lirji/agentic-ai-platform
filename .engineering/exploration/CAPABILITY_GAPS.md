# 与 langchain4j-platform 的业务及实现精细度差距

取证日期：2026-10-21。任务：`capability-gap-analysis-20261021`。本报告是能力分析，**五步改造已按用户要求暂停；以下建议不代表已实施或已批准的新契约**。

**结论：当前项目已经实现了可靠的知识问答和只读任务主链路，但知识业务的覆盖范围、日常管理流程、质量控制及多人运行能力，明显少于参考项目。更换为 LangGraph / Deep Agents / LlamaIndex，并没有自动迁入这些业务能力。** S0–S7 的切片验收通过，只能证明这些切片交付，不能证明新平台已经达到参考项目的业务深度。[E01、E24](EVIDENCE_INDEX.md)

最应补齐的三件事是：可持续运行的质量评测；带结构与生命周期的知识资料管理；从反馈到纠错、审核、发布和验证的知识运营流程。最不应做的是为了“看起来更完整”，直接复制参考项目的全部服务、四路召回和可选组件。

## Missing Capabilities：缺失的业务与管理流程

### G01　评测还没有成为产品能力

**现状 FACT：** 当前 QA 已覆盖真实问答、无资料拒答、引用、恢复与隔离，但使用少量合成资料，未提供评测集管理、固定基线、逐题对照或回归门禁。参考项目有 `QualityController/QualityService/QualityScoring` 与前端评测面板：数据集修订会使旧基线失效；运行绑定定义和权限上下文；计算文档级 Recall、Precision、MRR、Hit Rate 和延迟；同时检查总体与逐题退化。[E09、E24](EVIDENCE_INDEX.md)

**差距影响 INFERRED：** 无法判断“换分块器、加 Reranker、改模型”到底改善了哪些真实问题，也不能区分召回失败、排序失败、证据不足和生成错误。通过接口测试不等于用户问题答得更好。

**后续应具备：** 有版本的业务问题、正确证据、拒答及权限用例；同配置可重复运行；逐题结果和失败原因；检索、引用正确性、语义支撑、回答完整度、延迟及成本分别报告。参考项目的文档级评分也不能替代 chunk 级证据、答案正确性或真实业务标注。

**可观察验收：** 固定数据集重复运行可比；修改数据集/身份范围后不误用旧基线；故意降低召回能被逐题门禁发现；执行失败不能计为成功；拒答题和越权题单列。样本规模和通过阈值应由后续基线决定，不在本报告虚构目标数字。

### G02　资料格式覆盖与解析失败处理不足

**现状 FACT：** 当前只接受 `.txt/.md`、严格 UTF-8、最大 1 MiB；这是明确边界，不是 PDF “偶尔打不开”。参考项目存在原生 PDF、DOCX、XLS/XLSX、CSV、Markdown 的专用结构解析，其他部分格式走受限 Tika；支持有界 OCR、解析告警和独立解析进程，并有真实格式、Linux 容器、OCR 专项记录。[E02、E03、E25](EVIDENCE_INDEX.md)

**差距影响 INFERRED：** 用户必须手工转文本，页码、表格、扫描件信息容易丢失，后续搜索和引用质量从输入环节就受限。

**后续应具备/验收：** 先覆盖真实资料占比最高的 PDF、DOCX；区分损坏、加密、无可提取文字、部分提取和超限，提供可操作错误；保留解析器版本、结构与告警。扫描资料出现时再纳入 OCR 准确度与资源预算。实际样本必须验证原文完整度、乱码、表格结构及资源上限；只通过 MIME 注册或安装解析库不算完成。

### G04　发布版本字段尚未构成文档生命周期

**现状 FACT：** 当前受理生成新文档 UUID，初始版本固定为 1；有持久任务、发布指针及引用版本复核，但公开入口没有更新已有文档、删除或重索引。参考项目支持已有文档更新版本、删除、相关任务及分享操作。其同步兼容上传路径仍有“先清旧版再写新索引”的可见性限制；物理清理部分采用尽力而为，也不能整体视为原子一致实现。[E05、E06](EVIDENCE_INDEX.md)

**差距影响 INFERRED：** 资料修订只能上传成另一个文档，旧内容继续参与检索；无法从业务界面撤下过期材料；索引或解析策略变化时缺少统一重建入口。

**后续应具备/验收：** 更新、发布、撤下、删除、重索引分别有状态和权限；失败时保留可用发布版；并发更新冲突明确；删除后检索、问答、历史引用都服从同一可见性规则；重索引不伪装成内容更新；旧引用明确显示不可用或版本变化。参考项目的补偿/清理思路可借鉴，其同步兼容路径不应直接照搬。

### G06　缺少持续供给知识的来源同步

**现状 FACT：** 当前入口是用户上传。参考项目有绑定来源的 HTTP 增量同步，以及来源状态、外部记录到文档映射、手动轮询、暂停/恢复、重试和运行历史；来源配置与执行身份受服务端约束。未配置来源时功能不会自动产生数据。[E11](EVIDENCE_INDEX.md)

**差距影响 INFERRED：** 当知识来自持续更新的业务系统或文档站点时，当前只能人工重复上传，资料时效与责任人难以管理。

**触发与验收：** 先明确真实来源及更新/删除语义，再做一种来源；重复记录、游标重放、失败恢复、来源删除和身份变更必须可验证。不要在没有来源需求时先建设通用连接器平台。

### G09　缺少“发现问题—修正知识—确认生效”的运营流程

**现状 FACT：** 当前用户可以查看回答和引用，却没有反馈收件箱、候选知识、评审与发布管理。参考项目有反馈原因、候选编辑、内容绑定评估、`DRAFT → EVALUATED → APPROVED → PUBLISHING → PUBLISHED/PUBLISH_FAILED`、实际入库状态同步、发布后检索探测、历史审计和回滚草稿。前端调用真实 API；已有离线全链路和真实 MySQL 验证，部分模型/外部存储验证并未覆盖。[E10、E17、E25](EVIDENCE_INDEX.md)

**差距影响 INFERRED：** 系统知道一次任务成功或失败，却无法让运营者闭环处理“答案不对、资料缺失、知识过期”。这也是此前五步建议遗漏最明显的一项。

**后续应具备/验收：** 反馈能关联问题、引用与任务；编辑改变内容后旧评估/审批失效；发布必须以真实入库结果为准；发布失败可恢复；发布后探测对应实际新版本；回滚生成可审计补偿版本；无权人员不能审批/发布。候选文本包含某个短语的检查只能作为局部条件，不能代替完整知识质量评估。

### G10　正式身份与多人共享尚未形成可用业务

**现状 FACT：** 当前后端已有签名验证、内部令牌、scope、租户及所有者边界；React 使用仅面向 loopback 开发环境的会话桥，限定路由和同源，服务端签发短期令牌。它不是正式组织登录、成员管理或文档共享入口。参考项目有 Casdoor 接入、RBAC/文档分享及可选 ReBAC；知识服务配置中的 ReBAC 默认 `disabled`，不能把分享 API 的存在当作已启用强制授权的证据。[E16、E17](EVIDENCE_INDEX.md)

**后续应具备/验收：** 真实登录/退出/过期恢复、明确角色、个人与团队资料边界、授权及撤权。共享前后检索、引用、历史回答、在途任务必须同规则；不能仅前端隐藏按钮。此项在团队开放前是准入条件，当前不应误写为“后端没有鉴权”。

### G11　长期记忆与治理未迁入

**现状 FACT：** 当前持久化会话和任务，不代表已实现用户画像；问答仅使用指定上一轮作为有限上下文。参考项目有摘要记忆、JDBC 用户画像、待确认候选、批准/拒绝/修改/遗忘/置顶、过期及用户代次控制，防止旧抽取任务在清空后回填。[E12、E13](EVIDENCE_INDEX.md)

**触发与验收：** 长期个性化或跨会话助手确有需求时建设。用户能看到保存了什么、来自哪里并纠正/删除；撤销后旧任务不回填；过期/未确认内容不进入上下文；租户和用户隔离。单次资料问答无需为追赶参考项目而默认保存个人记忆。

### G20　参考项目的业务广度属于另一类差距

参考仓库还包含订单查询、Flowable 流程、SQL 分析、税票审核、语音/视觉、渠道接入和 MCP/A2A 协议入口；部分按配置启用，部分依赖独立服务。当前“解释/清单/草稿助手”仍围绕知识资料，不等价于能够读取业务数据、申请流程或执行操作的业务助手。[E01、E22、E23](EVIDENCE_INDEX.md)

这是**范围差异 FACT**；是否应建设为 **UNKNOWN**，须由实际业务决定。不能因为当前没有订单、税票服务就把知识平台判为缺陷。未来选一个真实场景，明确数据所有者、工具权限、确认、幂等和结果查询，再形成独立能力切片。

## Partial Capabilities：已有实现，但还不够细

### G03　可靠字节定位与结构化可读引用有距离

当前 `SentenceSplitter` 采用字符计数，512 大小、64 重叠、最多 100 块；映射回原文的 UTF-8 字节区间并进行摘要绑定，避免凭空生成引用位置。参考项目有标题、父子、语义等分块策略及结构化 splitter，并传递页、段、表、工作表、行列、提取方式和 OCR 告警。[E03、E04](EVIDENCE_INDEX.md)

**影响：** 当前在协议正确性上较严谨，但对标题上下文、跨块表格、长条款和用户定位原文支持有限。简单换更大窗口不能解决结构丢失。

**验收方向：** 片段保留标题/表头与来源；片段 ID 唯一且绑定内容/版本；混合中英文、代码、表格、跨页内容均有样本；引用界面能定位到人可理解的位置；以同一评测集比较分块效果，不能用策略数量充当质量。

### G05　幂等受理不等于内容去重和可运营入库

当前同身份、同幂等键能重放，同键变内容会拒绝；换一个键上传相同内容仍可创建新的文档。参考项目已有按内容摘要查重、可见性筛选、结构化重复响应，区分已发布文档与本人未完成任务，并有并发/真实 MySQL 及前端提示证据。[E02、E25](EVIDENCE_INDEX.md)

**影响：** 多次上传和改名上传可能形成重复资料、增加处理成本与相似候选，用户难以知道已有哪个有效版本。当前已有失败任务重试，不应写成“完全没有入库恢复”。

**验收方向：** 同内容不同名/不同请求能识别；不泄露无权文档；删除/旧版本不误挡新上传；未知提交结果继续使用原身份查询。批量进度、失败分类、部分成功和资源告警随真实批量需求补齐，不先假定参考项目已有无限制批处理能力。

### G07　两路融合已实现，模型精排与检索诊断未实现

当前真实链路是：查询 Embedding → Qdrant 向量与 ES 关键词各至多 100 个候选 → 按候选身份合并、RRF `1/(60+rank)` 累加 → MySQL 已发布块、租户/所有者、文档范围及批次摘要复核 → 排序 → Top K。检索 API 默认 K=5、上限 20；问答取 5。两路调用在 Java 中顺序执行；LlamaIndex 是授权检索适配层，没有独立模型精排。[E07、E08](EVIDENCE_INDEX.md)

因此用户此前提出的“合并去重 → RRF(60) → 权限/发布版本 → Top K”**已经有代码，不能再次列为从零待建功能**。融合按排名计算，不是把向量分数与 ES 分数直接相加。

参考项目支持配置化来源、查询扩展、有界并发召回、融合和精排；代码可组装向量、内存词法、ES、图谱来源，实际来源数取决于配置。Reranker 有 LLM/Jina/百炼等适配：应用 YAML 默认类型与标准 Compose 覆盖不同；Compose 选择百炼 `qwen3-rerank`。本轮确认的是实现和配置，没有确认当前线上调用或质量收益。[E07、E08](EVIDENCE_INDEX.md)

**真正缺的内容：** 授权候选池上的独立相关性模型；候选数量/阈值/超时/失败策略；来源贡献、RRF 名次、精排名次与耗时的诊断；同集对照。RRF 解决多路排名融合，不能替代 query–chunk 的相关性判断。

**后续正确约束：** 先过滤无权/未发布候选，再将足够数量的合法正文交给精排；精排后取 Top K；最终使用时继续复核权限与版本。不能先取 5 条才要求精排“救回”被排掉的相关内容。外部模型的数据边界、费用、失败可见性须明确。最终由哪个服务承载是后续设计，不在本报告直接改架构。

**验收方向：** 固定原两路 RRF 为基线；同资料、问题、权限和版本进行消融；报告有改善及退化的逐题证据；精排超时/无效索引/重复返回/预算不足有可预期结果；无权内容零外发。不能预设多一路或新模型一定更好。

### G08　有效引用不能证明答案受证据支撑

当前有“只用本次证据”的提示、无证据拒答、引用编号格式及来源/权限复核。这可以阻止部分伪造引用，但一句错误结论仍可能挂在真实引用上。参考项目有可选 LLM grounding 与输入 guardrail；grounding 评分失败可跳过该层，警告模式也不等于正确性保证。[E12](EVIDENCE_INDEX.md)

当前追问的检索主要依据本次问题，有限历史用于生成理解；不具备完整历史压缩和可评测的指代消解。需用“它是否支持”“上面的第二项”等真实追问验证，不能仅因为持久化了多轮就宣称模型理解完整上下文。

**验收方向：** 分开测试引用可访问、引用准确、结论受支持、回答覆盖问题；加入错误但引用合法、相互矛盾、无答案、注入内容和跨轮指代样本；明确不足时拒答/降置信/提示的产品行为。是否引入在线判别模型，先依据错误分布与成本决定。

### G12　框架集成尚未等于通用业务 Agent

当前 Deep Agents 只提供知识搜索与证据读取，最多 3 轮模型、5 次工具、2 次额外搜索；没有子 Agent、文件系统/命令工具或内部 checkpoint，analyze 是有界原子阶段，恢复可能重新执行并计费。外层 LangGraph 与中央任务负责恢复，这是有意收窄且已经验证的边界。[E14、E15、E24](EVIDENCE_INDEX.md)

参考仓库有链式/DAG 等 Agent API 和更广业务接口，但默认路由指向外部 AgentScope，Java agent-service 是回退路径；本轮不能把 Java 类存在直接算成当前默认 Agent 的实际执行行为。

**下一步价值：** 优先让一个研究任务能说明缺少什么证据、覆盖哪些问题、因何终止，并验证不同资料任务的结果质量；有真实业务场景时再扩展工具授权、人工确认、幂等与补偿。不能为了使用框架而开启任意工具、子 Agent 或额外数据库。

### G18　前端的主要差距是任务覆盖，不是换个界面样式

当前 React 已有上传、状态、检索、引用、会话、研究、助手及取消/恢复，未知提交结果、重试和窄屏行为有验收；这部分不能评价为只有展示壳。参考 Vue 工作台还绑定了质量评测、知识运营、来源同步、结构化来源、文档管理和记忆治理 API。[E17、E24、E25](EVIDENCE_INDEX.md)

后续每个能力应同时交付用户入口、状态解释、失败恢复和权限行为。验收以真实用户任务完成为准，例如“找到错误回答并发布修正知识”，而不是只多出一个管理页或一个成功按钮。

## Scaling Gaps：规模与协作后的缺口

### G13　已有分布式约束，缺少多 worker 与多租户的运行证明

当前中央任务用数据库行锁/`SKIP LOCKED`、租约代次和过期检查，PG 检查点由中央提交凭据约束；不能说完全没有并发设计。但当前问答/研究 worker 顺序领取两种图、绑定一个配置租户，既有验证不能证明多 worker 下的公平、吞吐及尾延迟。知识处理/检索也有本实例容量边界。[E06、E15、E24](EVIDENCE_INDEX.md)

参考项目有有界检索执行器、入库资源预算和公平准入专项；它们是可借鉴实现和实验，不是当前项目的容量结论。[E07、E25](EVIDENCE_INDEX.md)

**验收方向：** 同任务多 worker 抢占、失租者回写、取消竞态、下游慢响应、单租户堆积、多租户饥饿、重启恢复；同时记录排队时间、端到端延迟、资源及费用。先验证再扩副本，不能以 SQL 中出现 SKIP LOCKED 代替整链路证明。

### G14　已有基础指标，缺少业务诊断与处置流程

当前 Java 暴露 health/prometheus，有 Micrometer 计时、追踪关联和任务事件。参考项目另有模型监听、chunk 指标、共享观测模块、Prometheus 告警配置及配置验证。当前仍未形成可验证的 Java→Python→模型→索引统一诊断、业务质量面板及告警处置；跨服务完整关联是否满足目标为 NEEDS_VERIFICATION。[E18](EVIDENCE_INDEX.md)

**验收方向：** 一次失败能从任务定位到解析、召回、精排/生成、外部依赖和耗时；区分无证据、无权限、依赖失败及预算不足；报警对应可执行处置。审计应记录授权、知识修改、发布及重要模型/工具动作，保护原文和敏感信息，不只是采集更多日志。

### G15　实验预算与平台配额不是同一种能力

当前 Embedding/聊天使用有文件锁、失败关闭的本地累计预算账本及调用上限，保护本次试验费用；它不能直接证明多主机共享配额、租户限额、预留/结算和实际用量对账。参考项目有 token budget、Redis tracker 和服务端预留/结算 API，但相关能力按配置启用，不能宣称默认全平台强制生效。[E19](EVIDENCE_INDEX.md)

**验收方向：** 多实例竞争不超发、重复结算不重复扣减、取消/超时/未知结果有一致处理、恢复重复模型调用可归因；预估与实际用量分开。当前本地账本继续保留，不能靠清零账本获得“可用额度”。

## Engineering Gaps：交付、运行及文档

### G16　手工验证充分与持续交付能力仍有距离

当前依赖锁定、Java/Python/React 测试和真实组件验收已有证据，但两个当前仓库未提供 `.github/workflows` 流水线。参考仓库有 Java/前端、契约、配置和供应链等 CI 定义；同时其近期交付记录明确包含 SBOM 扫描失败和条件测试跳过。因此差距是自动化覆盖与可重复交付，而不是“参考 CI 全绿”。[E20、E24、E25](EVIDENCE_INDEX.md)

**验收方向：** 一个干净环境可按固定版本构建；变更触发适当 Java/Python/前端及契约验证；依赖扫描结果绑定提交；失败不能被成功摘要掩盖；手工真实模型验证单独保留预算与条件。测试条数不作跨项目质量排名。

### G17　本地可运行不等于部署与恢复可验收

当前以本机 Java/Python/Vite 和搜索组件 Compose 启动，缺少完整应用的可交付部署与生产环境准入证明。参考项目有服务 Dockerfile、Compose、Helm、迁移角色、运行加固与 dev_infra 迁移用的备份/导入工具；它们不能直接等同于日常备份与灾备流程。这些资产更丰富，但本轮未核验其生产 RPO/RTO 或全灾难恢复结果。[E21](EVIDENCE_INDEX.md)

**验收方向：** 固定制品与配置可重建；迁移身份和运行身份分离；在独立恢复环境还原 MySQL、对象原文、检查点，并确认索引与权威数据的重建关系；旧任务恢复、权限、引用和预算连续性一起验收。备份命令执行成功不等于恢复成功；不在本轮执行备份或部署。

### G19　阶段记录与当前能力说明需要分开

旧索引存在“S0 开始、前端未创建、Q/T 待落实”等历史描述，而后续实现已到 S7。参考仓库的旧能力报告同样早于后续质量/解析/记忆迭代，不能直接复用旧结论。[E26](EVIDENCE_INDEX.md)

**本轮处理：** 新报告绑定固定提交，修正相关顶层索引，保留历史 QA 的适用范围；进度仍以原 `PROGRESS_STATE` 为唯一状态来源。后续每项交付明确“已实现 / 已验证 / 已启用 / 已部署”，不同状态不互相替代。

## 当前值得保留的实现

本项目不是所有方面都落后：身份来自可信令牌；索引命中必须回到权威数据复核；准备结果/正文/向量与摘要绑定；双索引完成后才发布；中央任务与 PG 检查点有执行代次约束；会话交接先持久化；取消/重启恢复及未知提交结果已有真实验证；模型、工具和费用边界较明确。[E06、E07、E14–E16、E19、E24](EVIDENCE_INDEX.md)

这些能力要作为后续验收底线，不能为了迁入参考功能而退回默认 hash embedding、绕过权限、放宽工具边界，或引入第二套任务状态权威。

## 对此前五步建议的修正

此前建议顺序总体可以沿用，但覆盖深度不足：

1. “建立评测”应包含业务标注、拒答/权限、逐题退化、运行记录与反馈入口，不能只加一个脚本。
2. “扩展格式”应连同结构保真、解析告警、资源限制、来源定位和前端展示验收。
3. “完善生命周期”应覆盖更新/删除/重索引、内容去重、旧引用、知识纠错与审核发布；来源同步按需求另开。
4. “优化检索”以现有两路 RRF 为基线，引入独立精排及诊断，再决定查询扩展/其他召回；同时检验答案支撑与追问。
5. “多人运行”拆成身份共享、容量/配额、可观测、CI/部署与恢复验收，不能用一次本地启动代表全部完成。
