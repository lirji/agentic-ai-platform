# 能力演进方向与依赖

2026-10-21。**状态：建议路线，未进入实施。** 用户已暂停原五步改造，本轮仅形成对比依据。此文没有决定新服务边界、最终技术选型、接口 schema、工期或新增模型预算。当前状态仍见 [PROGRESS_STATE](../../docs/design/knowledge-first-20261020/PROGRESS_STATE.md)。

当前可恢复知识/任务底座可复用；近期应先获得质量证据，再补资料管理和运营流程。不要把整套参考平台迁入当成升级目标。

## Evolution Principles

1. 以完整用户任务验收：上传真实资料、维护版本、定位证据、得到可信答案、纠正错误、确认发布生效。
2. 每个改进都有前后对照；不以模型名称、框架数量、召回路数或测试条数判断业务提升。
3. 保留既有权限、权威数据校验、准备结果绑定、中央任务和预算底线。
4. 已实现、已验证、配置启用、目标环境可运行分别标记；历史失败和未覆盖项继续可见。
5. 优先迁入业务规则和失败处理经验，不复制参考项目全部架构与历史兼容路径。
6. 每一项具备界面、API、数据、错误/恢复、测试和文档；不只交付正常路径。
7. 本路线为后续决策输入；恢复时先读取本报告及现场状态，再冻结当期契约和切片。

## Capability Dependencies

用表格表达依赖，避免把阶段顺序误解为所有工作必须串行或全量同批发布。

| 能力节点 | 必要前置 | 可以先做的最小部分 | 不宜提前做的部分 |
| --- | --- | --- | --- |
| O01 质量基线 | 代表资料、标注和当前链路 | 固定两路 RRF/当前问答基线，问题反馈记录 | 未知资料上直接承诺提升比例 |
| O05 结构化资料 | O01 的真实格式样本 | PDF/DOCX 提取与来源保真 | 未出现扫描件需求就铺开全量 OCR |
| O02 生命周期 | 现有权威发布规则，O01 版本用例 | 更新/撤下/引用语义 | 无状态规则的物理删除和直接覆盖 |
| O06 去重/入库管理 | O02 状态；O05 告警 | 同内容查重和真实冲突提示 | 全格式全来源批量平台 |
| O07 检索/答案改善 | O01；代表性资料与发布版稳定 | 独立 Reranker 消融和逐题分析 | 同时改分块/召回/模型后声称某项收益 |
| O08 知识运营 | O01、O02；多人审批依赖 O03 | 反馈收件箱/候选编辑 | 无内容版本绑定的审批、伪发布成功 |
| O03 正式身份共享 | 明确身份源、角色和所有权 | 登录和可验证 owner 行为 | 只有 UI 分享按钮、后端权限默认关闭 |
| O11 多实例/费用/观测 | O03、目标负载及预算主体 | 对现有 worker 的竞争/故障实验 | 不验证就扩副本或清零旧预算 |
| O04 CI/事实同步 | 已有构建与验证入口 | 随任一能力交付加入相应检查 | 把跳过集成/模型替身写成全栈通过 |
| O12 部署恢复 | O04、O03、O11；环境及恢复要求 | 形成制品与独立还原验证 | 未批准目标的生产部署 |
| O10 来源同步 | O02、O06、O03，真实来源协议 | 一个来源的完整状态流 | 通用连接器市场 |
| O09 场景助手/记忆 | O01、O03及明确业务需求 | 一个只读业务任务或可治理记忆任务 | 任意工具、多 Agent、无确认业务写入 |

## Phase 1：建立可持续使用的质量基线

**对应 O01/O04；优先级 P1。**

- 代表样本覆盖当前文本、后续格式、短问/复杂问/追问、无答案、冲突资料、权限与旧版本。
- 正确证据与可接受答案由业务标注确认；参考合成语料仅作为可复用资产，不自动充当黄金答案。
- 保存配置、资料版本、身份范围、每路候选/最终结果、逐题评分、耗时与费用口径。
- 基线先运行当前“两路 + RRF60 + 权威复核”，如实暴露缺陷。
- 区分检索准确性、引用准确性、答案受支持程度与完整度；先有稳定人工标准，再讨论模型裁判。

**退出条件：** 相同输入可复现，数据集变化不误用旧基线；执行失败、越权和拒答有独立结果；可从一次错误定位下一改造方向。

**不代表：** 已提升效果、已接精排或已完成全部知识运营。

## Phase 2：让真实资料保留结构并可管理

**对应 O05/O02/O06，分别形成完整切片；优先级 P1。**

先完成 PDF/DOCX 等真实高占比格式、来源位置、告警和资源限制；同步覆盖标题/表格/代码的分块保真。然后明确并交付更新、发布、撤下/删除、重索引及旧引用，最后围绕这些状态加入安全内容去重和管理诊断。

**退出条件：** 用户可以上传实际文件并核对原文位置；更新失败保留既有可用版；删除/撤下对搜索、回答和引用一致生效；相同内容重复受理不泄露权限且行为明确；故障恢复不产生混合版本。

**依赖说明：** 生命周期并非要等所有格式都完成，但两者都必须使用同一文档/准备结果权威，避免独立实现两套版本语义。

## Phase 3：补知识运营，并用同集改善检索和答案

**对应 O08/O07；多人运营需先满足 O03。**

反馈收集可在 Phase 1 开始；完整候选编辑、评估、审批、发布状态同步、发布后探测和补偿版本依赖生命周期。用反馈和评测选出最常见失败题，再引入独立 Reranker，随后按需处理查询扩展、追问指代、证据冲突和答案支撑校验。

**退出条件：** 一条真实问题能够从反馈走到实际修正版本并验证生效；内容改变使旧评估/审批失效；精排相对基线的改善和退化都可见，延迟/费用/失败策略明确；没有向模型发送无权候选正文。

**为何修正原建议：** 原第四步只强调检索技术，缺少谁发现问题、谁修正资料、如何确认修正有效。这里把运营闭环纳入能力目标，不仅调整排名算法。

## Phase 4：按准入条件补多人和长期运行

**对应 O03/O11/O04/O12。不是一个大切片，也不必等前三阶段全部结束。**

| 独立交付部分 | 触发条件 | 验收结果 |
| --- | --- | --- |
| 正式身份/共享/撤权 | 第二位真实用户或远程访问之前 | 身份生命周期和多路径撤权一致 |
| 多 worker/公平/容量 | 并发或多租户负载出现 | 竞争、失租、取消、饥饿及尾延迟有证据 |
| 共享预算/归因 | 多实例或租户配额 | 预留、结算、未知结果、恢复重复调用可解释 |
| 观测/审计/告警 | 故障不能靠开发者现场排查 | 从业务任务定位问题并执行处置 |
| CI/依赖门禁 | 持续协作 | 固定提交的构建/契约/安全检查可复现 |
| 制品、迁移及恢复 | 长期环境交付 | 独立还原验证及环境准入，生产部署另授权 |

不能把“本机服务起来了”作为这些事项的共同验收；也不需要为了路线编号把身份安全拖到已经多人使用之后。

## Phase 5：由真实业务触发来源与助手扩展

**对应 O10/O09；P2。**

选择一个持续知识来源或一个具体业务任务，先完成最小完整链路。需要长期个性化时再加可确认/纠正/遗忘的记忆；需要外部业务数据时先明确只读权限；任何写入/审批/通知都应有独立业务契约和授权。

**退出条件：** 用户任务有实际收益证明，权限、数据生命周期、重复调用和失败恢复可验证。参考的订单、流程、税票、语音等模块不默认纳入本阶段。

## Future Exploration

图谱召回、语义缓存、更多重排模型、多 Agent、多模态及渠道开放都须由固定基线和真实需求触发。复杂度、费用和维护成本要与业务收益一起评估；条件不成立时保留现有两路及有限工具。

恢复实施前只需解决与当期切片有关的未知项：代表资料和标注责任、实际格式、知识内容责任人、身份来源/共享规则、目标负载与环境。不要一次要求用户决定所有远期技术。最终方案和实施顺序在用户明确恢复后，沿现有设计/契约/进度体系更新。
